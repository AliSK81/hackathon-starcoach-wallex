# ML / RL Models and LLM-Agent Evidence for a 3-day Wallex Hackathon

**Scope**: Is ML/RL worth it in 3 days versus LLM-over-features; how to use cheap ML (LightGBM) as a tool the LLM calls; walk-forward protocol; leakage pitfalls; what the literature actually reports about LLM trading agents and their biases.
**Researched**: 2026-10-21
**Repos+commits / sources**:
`microsoft/qlib@5435523` (MIT), `AI4Finance-Foundation/FinRL@c0018c2` (MIT), `AI4Finance-Foundation/FinGPT@fdb04c9` (MIT), `freqtrade/freqtrade@0db79d3` (GPL-3.0; FreqAI in `freqtrade/freqai/`), `agiprolabs/claude-trading-skills@981e1d7` (MIT; `skills/signal-classification`, `skills/walk-forward-validation`), `HKUDS/Vibe-Trading@9081946` (MIT; `agent/src/skills/ml-strategy/SKILL.md`), `stefan-jansen/machine-learning-for-trading@35d6e2b` (MIT; ch. 07, 12, 24).

## TL;DR
- **Recommendation: LLM-over-deterministic-features as the decision maker; add ONE cheap LightGBM (or logistic) "P(up over next k hours, net of cost)" model as a callable tool/feature, retrained by walk-forward. Do NOT build an RL agent in 3 days.** Evidence: RL baselines are the weakest rows in every LLM-agent paper table (FinMem/FinCon/CryptoTrade), FinRL's reward is raw portfolio delta with no risk terms, and freqtrade itself says its RL reward function "is *not* for live production" (`freqtrade/docs/freqai-reinforcement-learning.md:139`).
- **Published LLM-agent performance is not trustworthy as evidence of live profit.** TradingAgents (3-month window, 3 stocks) reports Sharpe 5.60-8.21 and the authors themselves flag it exceeds expected ranges; FinMem/FinCon tune on tiny samples (FinMem picked its risk profile by test return); the independent long-horizon test FINSABER (2004-2024, 100+ symbols) finds the advantage "deteriorates significantly": LLM agents lag Buy&Hold in bull years and lose more in bear years.
- **Crypto-specific evidence is weak**: CryptoTrade (EMNLP 2024; BTC/ETH/SOL daily, 3 windows) beats Buy&Hold only in the ETH bull window (25.5 % vs 22.6 %; trails B&H on BTC and SOL bull) and is negative in most sideways/bear windows (it only reduces the SOL bear loss: -16.3 % vs -36.1 %) (tables below). The final EMNLP abstract says it beats time-series baselines but not traditional signals.
- **Look-ahead/memorisation is a measured, severe problem for LLM backtests** (FinCAD: up to −67.1 % in-sample return correction; Look-Ahead-Bench: significant look-ahead alpha decay in Llama 3.1/DeepSeek 3.2; BlindTrade: anonymise tickers). Consequence for us: LLM decisions cannot be honestly backtested on pre-cutoff history without anonymisation; use (a) deterministic-skeleton backtest, (b) LLM on anonymised/after-cutoff windows, (c) live shadow test (judges value it: 20 pts).
- **FreqAI is the best design reference** for the ML tool: `train_period_days`/`backtest_period_days` sliding retraining, `shuffle=False` splits, features scaled with MinMax fit on train only, outlier gate `DI_threshold` (dissimilarity index) and `use_SVM_to_remove_outliers`, `do_predict` flag so predictions are masked when the input is out-of-distribution.
- With ~60 days of hourly candles x 6-8 symbols (~10k rows, heavily autocorrelated labels), expect AUC around 0.50-0.56 at best (my estimate, unverified); use it only as a tie-breaker feature and as an explicit "model confidence" input. The LLM should see its calibrated probability AND its out-of-sample hit-rate so it can discount it.
- Pre-trained LLM sentiment (FinGPT v3.x: weighted F1 0.882 FPB, 0.874 FiQA-SA, 0.903 TFNS, 0.643 NWGI) is English-news-centric; for a 3-day Iranian-exchange contest, have the main LLM read headlines directly (if any news source is permitted) rather than fine-tune.
- Leakage checklist is in Findings 6; the most common bugs found in the repos read: whole-frame min/max normalisation, scaler fit on all data, overlapping labels without purge, picking hyper-parameters by test return.

## Findings

### 1. Qlib (skim): workflow and Alpha158
- Workflow in YAML: data handler -> dataset segments -> model -> `SignalRecord`, `SigAnaRecord`, `PortAnaRecord` (`qlib/examples/benchmarks/LightGBM/workflow_config_lightgbm_Alpha158.yaml`). Example uses fixed segments `train 2008-2014`, `valid 2015-2016`, `test 2017-2020-08` (single split, no walk-forward) and LGBModel hyper-params `learning_rate 0.2, max_depth 8, num_leaves 210, lambda_l1 205.7, lambda_l2 580.98, colsample_bytree 0.8879, subsample 0.8789` (heavily regularised, tuned on CSI300 daily data). Backtest costs `open_cost 0.0005, close_cost 0.0015, min_cost 5`, `deal_price: close`.
- `Alpha158` (`qlib/qlib/contrib/data/handler.py:98-157`; feature definitions `qlib/qlib/contrib/data/loader.py:117-290`): groups `kbar` (KMID, KLEN, KMID2, ...), `price` (windows [0]), `volume`, and `rolling` operators over windows `[5,10,20,30,60]`: ROC, MA, STD, BETA, RESI, MAX, MIN, QTLU/QTLD, RSV, IMAX/IMIN/IMXD, CORR, CORD, CNTP/CNTN/CNTD, SUMP/SUMN/SUMD, VMA/VSTD/WVMA, VSUMP/VSUMN/VSUMD. Label (`handler.py:89-90`): `Ref($close,-2)/Ref($close,-1) - 1`, i.e. the return from t+1 close to t+2 close (trade at next close because the signal is known after the close of t). Good pattern: **label starts after the next executable price, not at the current close.**
- Takeaway: borrow the idea (normalised, scale-free rolling features: ratios to the current close, rank/quantile and count-up features) not the framework (heavy, daily CN-equity oriented, cross-sectional ranking objective).

### 2. FinRL (env design, rewards, caveats)
- `finrl/meta/env_stock_trading/env_stocktrading.py`: constructor args `hmax` (max shares per trade per asset), `initial_amount`, `buy_cost_pct`, `sell_cost_pct` (per-asset arrays), `reward_scaling`, `turbulence_threshold` (`:25-49`). Action = vector in [-1,1] scaled by `hmax`; sells processed before buys (`:329-340`). Turbulence >= threshold forces liquidation of all positions (`:148-170, :319-321`).
- **Reward (`:377-381`)**: `reward = (end_total_asset - begin_total_asset) * reward_scaling`: raw one-step change in portfolio value; no drawdown, volatility, turnover or cost-awareness beyond the cost deducted from cash. This is exactly the kind of reward that overtrades or collapses to buy-and-hold; there are alternative env files (`env_stocktrading_cashpenalty.py`, `env_stocktrading_stoploss.py`).
- State: [cash] + prices + holdings + technical indicators. Default `INDICATORS` in `finrl/config.py:21-30`: `macd, boll_ub, boll_lb, rsi_30, cci_30, dx_30, close_30_sma, close_60_sma`. Defaults `A2C_PARAMS {n_steps 5, ent_coef 0.01, learning_rate 0.0007}`, `PPO_PARAMS {n_steps 2048, ent_coef 0.01, learning_rate 0.00025 ...}`; train range 2014-2025, test 2026-01-01..2026-03-20 (`config.py:10-16`): >10 years of daily data to train; we have days.
- No built-in walk-forward, purging, or significance testing. README has only a disclaimer (line ~381: "academic purposes ... nothing herein constitutes financial advice"). Known overfitting issues are not documented in the repo itself (I found no such section); evidence of weak RL results comes from the agent-paper tables below (A2C/PPO/DQN often negative, COIN: "DRL agents did not converge").
- Long-only maps naturally (actions bounded, no shorting by default). Fee-awareness: only via `buy_cost_pct/sell_cost_pct` (set to Wallex fee).

### 3. FreqAI (inside freqtrade) - the useful reference
- Models shipped (`freqtrade/freqai/prediction_models/`): `LightGBMClassifier/Regressor(+MultiTarget)`, `XGBoostClassifier/Regressor/RF`, `SKLearnRandomForestClassifier`, `PyTorchMLP*`, `PyTorchTransformerRegressor`, `ReinforcementLearner`.
- Features: user fills `feature_engineering_expand_all` (expanded across `indicator_periods_candles`, `include_timeframes`, `include_shifted_candles`, `include_corr_pairlist`), `feature_engineering_expand_basic`, `feature_engineering_standard` with columns prefixed `%`. Example template (`freqtrade/templates/FreqaiExampleStrategy.py:60-95`): `%-rsi-period, %-mfi, %-adx, %-sma, %-ema, bb_width=(upper-lower)/middle (stds=2.2), close/bb_lower, %-roc, %-relative_volume=volume/rolling(period).mean()`. Feature count multiplies: timeframes x features x correlated pairs x shifted candles x periods (`docs/freqai-feature-engineering.md:181`), a recipe for hundreds of features on little data; our version should keep ~25-40.
- Labels: prefixed `&`; example `&-s_close = close.shift(-label_period_candles).rolling(label_period_candles).mean()/close - 1` (`FreqaiExampleStrategy.py:192-199`) with `label_period_candles 20` in `config_examples/config_freqai.example.json:68`; entry rule `do_predict==1 & &-s_close>0.01`, exit `&-s_close<0` (`:238-265`). Targets are *recomputed per training window* so backtests don't leak labels (`docs/freqai-running.md:71`), but features are computed once on the whole range: the doc warns the user to ensure no look-ahead.
- Walk-forward retraining: `train_period_days: 15`, `backtest_period_days: 7` (example config lines 53-54); `split_timerange(tr, train_split=28, bt_split=7)` slides the window (`data_kitchen.py:316-`); `live_retrain_hours`, `expiration_hours` control live retraining/staleness (`:520-555`). Docs warn that a true FreqAI backtest with fine retrain frequency "would take a very long time"; best test = dry run.
- Splits: `shuffle` defaults False (`data_kitchen.py:136-137`); example `test_size 0.33`. Recency weighting: `weights = exp(-arange(n)/(weight_factor*n))[::-1]` (`:408-417`).
- Pipeline (`freqai_interface.py:560-590`): `VarianceThreshold(0)` -> `MinMaxScaler(-1,1)` (fit on training only) -> optional PCA (0.999 var) -> optional `SVMOutlierExtractor(nu=0.01, shuffle=False)` -> optional `DissimilarityIndex(di_threshold)` -> optional DBSCAN -> optional Gaussian noise (`noise_standard_deviation`). `outlier_protection_percentage` default 30 (if more than 30 % flagged, ignore detection and make **no** predictions).
- **Dissimilarity Index** (`docs/freqai-feature-engineering.md:319-351`): normalised-space Euclidean `d_ab`; characteristic distance `d̄ = mean over training pairs`; for a new vector `X_k`, `d_k = min_i d(k,i)`; `DI_k = d_k / d̄`; prediction discarded when `DI_k > DI_threshold` (example config 0.9; docs "typically < 1"). Cheap, implementable in 20 lines with numpy/sklearn NearestNeighbors; gives the LLM an explicit "model is extrapolating" flag.
- `continual_learning` is flagged by the authors as "naive ... high probability of overfitting/getting stuck in local minima" (`docs/freqai-parameter-table.md:21`). Hyperopt advice: optimise only entry/exit thresholds, not feature windows (`freqai-running.md:158`).
- RL in FreqAI: `Base5ActionRLEnv` (neutral, long enter/exit, short enter/exit); the example reward (`prediction_models/ReinforcementLearner.py:112-157`) literally returns `+25` for entering a trade and `-1` for being flat, `-trade_duration/max_trade_duration` for holding; docs say it is a "showcase ... *not* for live production" (`freqai-reinforcement-learning.md:139`). Illustrates reward-hacking risk.

### 4. FinGPT (sentiment pipelines)
- Repo is mostly LoRA fine-tuning notebooks plus data-pipeline code. Sentiment: instruction-tuned Llama2/ChatGLM models "FinGPT v3.1-3.3" benchmarked on FPB, FiQA-SA, TFNS, NWGI (README table lines ~137-141, weighted F1: v3.3 0.882/0.874/0.903/0.643; cost "$17.25, 17.25 h on 1x RTX 3090"). Prompt: "What is the sentiment of this news? ... {negative/neutral/positive}" (README ~185).
- `fingpt/FinGPT_Forecaster/` (`prompt.py`, `data.py`, `market_sentiment.py`): LLM gets past-weeks news + basic financials, outputs "[Positive Developments] / [Potential Concerns] / [Prediction & Analysis]" for next-week stock movement (README line 17; system prompt `prompt.py:~174`). Weekly horizon, US equities via Finnhub/Yahoo - not transferable to a 3-day Wallex crypto test.
- In the FinMem table FinGPT is among the worst baselines (TSLA −7.46 %, COIN −88.78 % CR): it did not translate sentiment to returns. Relevance for us: low. If any news/Telegram signal is used, have the primary LLM score it with a fixed rubric and log the raw text; do not fine-tune.

Implications for our design:
1. None of the cited papers uses crypto spot with fees at 0.1 %/side or hourly decisions; none shows reliable live outperformance. Present our LLM as a *selector/risk-aware reasoner* over deterministic features, not as an alpha oracle, and do not claim paper Sharpe ratios.
2. The only fair evidence of the LLM layer is **live shadow + live trading logs**; keep a deterministic baseline (rules-only) running in shadow beside it so judges see the LLM's incremental value (supports "Real AI use 35" and "Backtest+shadow 20").
3. Mitigate look-ahead when backtesting the LLM: anonymise symbols ("ASSET_A"), strip absolute dates and round prices to relative indices, use only the feature JSON (no raw news with named events), and prefer test windows after the model's knowledge cutoff (a model with cutoff earlier than the window; check the vendor's published cutoff - not verified here). Even then partial memorisation remains (the FinCAD/Look-Ahead-Bench caveat).

### 6. Cheap ML as a tool for the LLM: LightGBM probability of up-move
Reference material: `ctsk/signal-classification/SKILL.md` (XGBoost/LightGBM, labels, calibration, walk-forward, SHAP), `ctsk/walk-forward-validation/SKILL.md` (purge/embargo/CPCV/deflated Sharpe), `vt/ml-strategy/SKILL.md` (`walk_forward_predict`), FreqAI (above), stefan-jansen ch. 07 (triple-barrier, IC inference, multiple testing) and ch. 12 (GBM).

**Design (recommended)**
- Tool `ml_signal(symbol) -> {p_up_net: float, auc_oos: float, brier: float, n_train: int, di: float, trusted: bool, top_features: [...]}`.
- Label: binary `y = 1 if max over next h bars of (close_{t+i}/entry - 1) hits +TP before -SL` (triple barrier with TP = 2·ATR, SL = 1.5·ATR, horizon h = 12-24 hourly bars) OR the simpler `ret_{t+1..t+h} - round_trip_cost > 0`. The label must be net of Wallex cost `c` (file 06). Entry price = next bar open/ask (Qlib-style `Ref(close,-1)` offset, `handler.py:89`).
- Features: the same deterministic set the LLM sees (file 06), all scale-free (returns, ratios, percentiles, z-scores), 25-40 columns; add BTC context features; **no raw price levels, no calendar IDs beyond hour-of-day/day-of-week**.
- Model: `LGBMClassifier(n_estimators=200, max_depth=3-4, num_leaves 8-15, learning_rate=0.03-0.05, subsample=0.8, colsample_bytree=0.8, min_child_samples>=100, reg_lambda>=10, n_jobs=1, random_state=42, deterministic=True)` (cf. `ctsk/signal-classification/SKILL.md:161-181` uses depth 4, lr 0.05, 200 trees; `vt/ml-strategy` uses GB depth 3 lr 0.05 100 trees; Qlib uses very heavy L1/L2 regularisation). Baseline to beat: logistic regression on 6 features. Keep model files + seed + feature hash in the repo for reproducibility.
- Calibration: isotonic via `CalibratedClassifierCV(cv=TimeSeriesSplit)`, or Platt (`ctsk/signal-classification/SKILL.md:68-80`); with ~10k autocorrelated rows prefer Platt/logistic to avoid overfit isotonic steps.
- Output gating: return `trusted=False` and `p_up=None` when `DI > 0.9` (FreqAI-style), fewer than N training rows, or the rolling OOS AUC < 0.52. The LLM prompt receives `p_up`, `auc_oos`, `di`; the risk gate never reads it.
- Retrain every 12-24 h in live (FreqAI `live_retrain_hours` analogue) using last 30-45 days; save the model snapshot per retrain, log its id in each decision record.
- Compute cost: LightGBM on ~10k x 40 trains in seconds on CPU; judges can re-run.

**Walk-forward validation protocol (required before using the tool)**
1. Data: 60-90 days of 1h bars per symbol from `/v1/udf/history` (reindexed; zero-volume bars flagged), symbols pooled with a `symbol` embedding avoided (use scale-free features only) or per-symbol models if enough rows.
2. Splits: rolling `train = 30 d (720 bars)`, `gap/embargo = max(h, 2x label horizon)` (`ctsk/signal-classification/SKILL.md:102-109` gap = horizon; `ctsk/walk-forward-validation/SKILL.md:94` "crypto rule of thumb embargo >= 2x label horizon"), `test = 3 d (matches contest length)`, `step = 1 d`. Equivalent to Vibe-Trading `walk_forward_predict`: label at row t is only usable once `t + horizon <= i` -> `train_stop = i - prediction_horizon + 1` (`vt/ml-strategy/SKILL.md:~126-134`).
3. Purging: drop training rows whose label window overlaps the test range (`purge_train_indices`, `ctsk/walk-forward-validation/SKILL.md:66-79`).
4. Fit scalers/imputers/feature-selection INSIDE each training fold only (FreqAI pipeline is fit on train; `vt` fits `StandardScaler` on train only).
5. Metrics on concatenated OOS predictions: AUC, Brier, calibration curve, IC (Spearman of p vs forward net return), and **net PnL of the rule "enter if p > thr, TP/SL bracket" with fees and spread**, vs always-long and random-entry baselines; report per-regime and per-day (3-day windows give ~20-60 independent windows at best).
6. Multiple-testing control: log every config tried; report the deflated Sharpe / number of trials (`ctsk/walk-forward-validation/SKILL.md:108-` DSR; stefan-jansen `07_defining_the_learning_task/07_multiple_testing.py`). Fix hyper-parameters a priori; no tuning on the final 7 days.
7. Accept the model only if OOS AUC >= 0.53 on >= 70 % of folds and net expectancy per trade > 0 after cost; otherwise ship the LLM without ML and say so in the doc (still honest, still scores).

**Leakage pitfalls (each found in sources read)**
- Whole-frame normalisation: freqtrade-strategies `lookahead_bias/{DevilStra,GodStraNew,Zeus,wtc}.py` (min/max/MinMaxScaler over full series).
- Rolling stats computed on the full frame in backtest (`Strategy004.py:107-110` comment).
- Labels that overlap the test window (no purge/embargo) - `ctsk/walk-forward-validation/SKILL.md:17` "label overlap".
- Using the current bar's close to decide AND to fill at the same close; features need `shift(1)` or decide at close and fill at next open/ask (Donchian `shift(1)` in FinanceToolkit).
- Hour-of-bar completeness: Wallex omits empty bars, so naive `shift(24)` is wrong; reindex to a full hourly grid first.
- Selecting thresholds/risk profile by test return (FinMem's own caveat).
- LLM-specific: named assets/dates enabling memorisation; prompts containing future text; non-deterministic outputs (set `temperature 0`, fixed seed where available, log raw responses).
- Survivorship: candidate coins chosen today because they performed well recently.
- Shuffled K-fold CV (FreqAI keeps `shuffle=False` for this reason).

### 7. Is ML/RL worth it in 3 days? Decision matrix
| Option | Dev time | Data need | Evidence of value | Risk | Verdict |

## Recommended design decisions for the hackathon
1. Architecture: `features (deterministic) -> {rules candidates, ML p_up tool} -> LLM agent (tool-calling, JSON output) -> deterministic risk gate (position cap, stop, daily loss limit, min notional/step rounding, cost gate) -> execution`. The ML tool is optional for the LLM; the risk gate ignores ML/LLM confidence except for sizing within a cap.
2. Ship LightGBM only if the walk-forward report passes the acceptance rule (Findings 6, step 7). Always publish the report (Backtest+shadow 20 pts) even if the model fails; a documented negative result still demonstrates rigor.
3. Treat paper numbers as marketing; cite FINSABER and look-ahead papers in the README as the reason we run a shadow test and an anonymised replay.
4. Shadow-test plan: run the full LLM stack live without orders for >= 24 h before real orders; run the rules-only baseline in parallel; compare decisions and counterfactual PnL net of cost.
5. Keep LLM temperature low (0-0.3, as FinCon used 0.3), fixed prompt versions, JSON schema, retry-with-validation, timeouts; deterministic fallback = hold/flat. Log every call.
6. No RL. If time remains, spend it on cost-aware execution (limit at bid+1 tick, timeout) and the TMN end-state liquidation routine.
7. Retrain cadence: model refit every 24 h at most (3-day window = 3 refits); version and log each; freeze the model during the final 12 h to avoid last-minute instability (Execution stability 15).
